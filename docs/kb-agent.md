# KBAgent

KBAgent 是一个面向企业内部知识库的 AI Agent。项目以 FastAPI 提供接口，以 LangGraph 编排多节点 Agent 流程，以 OpenViking 提供知识库检索能力，并结合 PostgreSQL、pgvector、mem0 和 Langfuse，形成可追溯、可中断、可继续的企业问答服务。

它适合用于产品文档、技术资料、项目规范、论文笔记和内部资源目录等知识库场景。系统不会只依赖模型的通用知识回答问题，而是优先检索 OpenViking 中的证据，再根据证据生成答案和资源路径。

## 账号、鉴权与会话

KBAgent 支持用户注册和登录，并使用 JWT 令牌保护聊天与会话接口。前端在请求中携带 `Authorization: Bearer <token>`，后端据此识别用户和当前会话。

每次对话都归属一个会话（session）。用户可以创建、查询和删除会话，也可以读取该会话的历史消息。会话首次收到用户问题后，系统会异步调用模型生成简短标题；即使模型命名失败，也会保留根据首条问题生成的临时名称，避免出现空会话。

## 企业知识库检索

知识库由 OpenViking 管理，资源使用 `viking://resources/...` URI 标识。KBAgent 支持三类检索相关操作：

- **`list_resources`**：读取知识库根目录下的系统/资源目录。例如返回 `Revin`、`psLoss` 等真实可选系统，供后续缩小检索范围。
- **`find`**：首选语义检索方式。系统根据用户问题查找语义相关的文档、摘要或正文片段，并保留原始 URI、层级和相关度分数。
- **`grep`**：当语义检索和查询改写都无法得到足够证据时，使用关键词或正则模式在指定系统范围内查找文本命中位置。

检索完成后，SSE 的 `tool` 事件会返回本次命中的具体文档 URI。前端可以据此展示“系统正在检索什么”和“找到了哪些文档”，而不是只显示一个笼统的加载状态。

## 系统范围确定

企业知识库的根目录下可能有多个系统。对于首次需要检索的问题，KBAgent 会先调用 `list_resources` 获取真实目录列表，再让模型根据**当前问题**判断是否能确定所属系统。

模型不能自由编造系统 URI：它只能从 OpenViking 实际返回的候选目录中选择，后端会进行精确匹配校验。只有模型判断充分且候选匹配成功时，检索范围才会从 `viking://resources` 缩小为类似 `viking://resources/Revin` 的系统 URI；否则仍在根范围检索。

这个范围仅对当前问题有效，不会从历史对话中推断或沿用系统范围，避免前一轮讨论某个系统影响后续独立问题。

## 多阶段 Agent 检索流程

KBAgent 的检索不是无限循环的自主搜索，而是一条有明确边界的流程：

```text
用户问题
  → 整理请求、分析意图和回答要求
  → 确定知识库系统范围（可选）
  → 首轮 find 语义检索
  → 融合结果并补全正文证据
  → 评估证据是否足够
  → 生成答案并校验
```

若首轮 `find` 的证据不足，系统会先进行一次查询改写后重新执行 `find`；如果仍不足，再构造关键词执行一轮 `grep`。若仍没有足够证据，则触发 HITL 请求用户补充信息。用户补充后会重新走一次受限检索流程；若仍失败，系统会明确返回“知识库中检索不到足以回答该问题的信息”。

这种设计可以控制检索成本，也避免证据不足时在同一问题上无限重试。

## 证据融合与正文补全

OpenViking 的 `find` 结果可能是目录摘要、概览或正文层级，且不同检索任务可能命中同一个 URI。KBAgent 会对候选结果去重、按相关度和证据层级排序、融合多轮检索结果。

对于只含摘要但可能与问题相关的资源，系统会继续读取更完整的内容，形成 `selected_evidence`。这一步保证后续评估与回答看到的不只是目录描述，也尽可能包含实际正文证据。

## 回答要求与证据评估

意图分析节点会把用户问题拆分为 `answer_requirements`。每项要求都有优先级和证据来源类型，例如知识库事实、可信用户上下文，或二者结合的个性化建议。

项目当前约束每轮最多一个 `required` 要求：只有用户原问题中明确要求、且回答必须具备的内容才标记为必须项；其他延伸说明归为 `optional`。这样不会因为可选的推荐、背景介绍或补充内容缺少资料而不断触发检索循环。

`evidence_grader` 在答案生成之前工作。它检查现有证据是否覆盖必须项：

- 必须项已有充分证据时，允许进入答案生成；
- 必须项缺少证据时，路由到查询改写、`grep` 或 HITL；
- 可选项缺失不会让必须项判定失败。

## 证据驱动回答与引用

`answer_generator` 只接收当前问题、用户角色、回答要求、已选证据和修订要求。对于来自知识库的结论，提示词要求在关键结论附近使用：

```text
[来源: viking://resources/...]
```

文档 URI 本身来自 OpenViking 的检索和读取结果，不由模型创建；模型负责在回答中引用传入证据里的 URI。对于缺少证据的内容，系统应省略、说明无法确认，或将其作为可选项处理，而不是编造事实。

## 答案忠实度校验

`groundedness_verifier` 在草稿生成后执行，用于检查“证据足够”是否真的转化为“答案忠实”。它会检查：

- 必须回答项是否在草稿中实际覆盖；
- 是否出现无依据或与证据冲突的结论；
- 用户角色相关的建议是否同时符合可信用户上下文和知识库事实；
- 回答中引用的 URI 是否来自当前检索到的证据范围。

校验结果可以让答案直接通过、要求 `answer_generator` 修订一次，或在发现必要知识库证据不足时返回检索阶段。通过校验后的草稿再由 finalizer 流式整理为最终回答。

## HITL 人工补充

当系统无法仅靠当前问题和知识库完成回答时，会触发 Human-in-the-Loop（HITL）中断，而不是猜测用户意图。

目前支持两类 HITL：

- **身份确认**：返回固定角色选项，例如产品经理、开发者和新员工。前端提交固定值，不依赖模型再次解析身份。
- **系统与问题补充**：返回 OpenViking 实际目录形成的系统选项，并要求用户同时选择系统 URI、补充具体问题、对象、版本、场景或期望结果。

HITL 通过 LangGraph Checkpoint 保存中断状态。用户提交补充信息后，后端使用同一会话恢复流程，而不需要从头丢失上下文。

## 角色化回答与 Mermaid 图

系统会根据已确认的用户角色调整回答重点。例如开发者更关注接口、实现和排障步骤；产品经理更关注能力边界、流程和业务影响；新员工更适合获得资源目录和学习建议。

当角色为产品经理或开发者，且问题涉及流程、架构、依赖关系等适合可视化的内容时，模型可以按需在 Markdown 中输出 Mermaid 图。该功能不是每次回答的强制输出，避免为普通问答增加无意义图表。

## SSE 流式交互

流式聊天接口使用 `text/event-stream`。除正常答案文本外，前端还能处理以下事件：

- `data:`：普通回答片段和完成事件；
- `tool:`：LangGraph 节点流转，以及 OpenViking `list_resources`、`find`、`grep` 的开始、完成或失败状态；
- `hitl:`：身份确认或系统/问题补充请求，选项字段位于事件顶层；
- `error:`：流式调用过程中的内部错误。

`tool` 完成事件的 `metadata.documents` 会携带最多十个去重后的命中文档/目录信息。`find` 通常包含 URI、层级和分数，`grep` 可包含命中行号，`list_resources` 包含系统目录名称和 URI。

## 记忆机制

KBAgent 使用两层记忆：

- **短期记忆**：LangGraph 的 AsyncPostgresSaver 将图状态和消息保存在 PostgreSQL Checkpoint 中，并以会话 ID 作为线程标识。它用于恢复上下文、恢复 HITL 中断以及读取会话历史。
- **长期记忆**：mem0 将可长期复用的语义记忆写入 pgvector，并按 `user_id` 隔离。后续对话可召回与该用户相关的偏好、背景或长期上下文。

会话是一次连续对话的边界；长期记忆则跨会话服务于同一用户。

## 可观测性、数据与部署

项目使用 PostgreSQL 存储账号、会话和 LangGraph Checkpoint，使用 pgvector 支撑长期记忆向量检索。Langfuse 用于追踪模型调用和 Agent 节点，Prometheus 与 Grafana 用于服务指标和监控面板。

应用支持 Docker Compose 部署。`app` 服务可使用预构建的 `linux/amd64` 镜像启动，数据库可独立持久化和升级。镜像在构建阶段会预置 tiktoken 的 `cl100k_base` 编码缓存，降低服务器无外网时因 tokenizer 下载失败而无法启动的风险。
